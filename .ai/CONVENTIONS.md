# Правила разработки и сопровождения контекста

Обновлено: 2026-10-31. Ниже — рабочие договорённости для следующих задач;
описание существующего кода смотри в ARCHITECTURE.md.

## Перед задачей

1. Прочитай `AGENTS.md`, PROJECT, CURRENT_TASK и STATE; для реализации — ARCHITECTURE и этот файл.
2. Проверь `git status --short` и текущий коммит. Не перезаписывай чужие изменения.
3. Запиши в CURRENT_TASK конкретную цель пользователя, границы и критерии готовности.
4. Прочитай файлы нужного сценария. Код и конфигурация имеют приоритет над устаревшими описаниями.

## Код

- Сохраняй React + TypeScript + Vite и обычный CSS, если задача не требует смены подхода.
  Новые библиотеки добавляй только с понятной необходимостью; обновляй lockfile вместе с package.json.
- Компоненты и файлы компонентов — PascalCase; функции, переменные, hooks — camelCase;
  типы — PascalCase; константы-каталоги — UPPER_SNAKE_CASE. Новые hooks начинай с `use`.
- Используй функциональные компоненты, именованные экспорты по текущему образцу,
  `import type` для типов, относительные импорты; существующая разметка использует BEM-подобные CSS-классы.
- Не выполняй мутации и побочные эффекты внутри render или state updater:
  StrictMode может повторять вызовы. Существующие отклонения перечислены в STATE.
- Игровые операции держи в store, баланс — в `content.ts`, общие типы — в `types/game.ts`.
  При смене эффектов улучшений согласуй `deriveStats`, определения и UI.
- Сохраняй совместимость сейва. Изменение ключей/структуры требует продуманной миграции
  и проверки старого сохранения; не сбрасывай пользовательский прогресс попутно.
- Для Telegram-вызовов учитывай браузерный запуск. Данные `initDataUnsafe` не являются серверной авторизацией.
- Для UI используй существующие ассеты; учитывай safe area, мобильную высоту, переполнение и кликабельные зоны.
  Навигация earn и остальных вкладок реализована отдельно.
- Русский — язык документации и основного интерфейса; существующие подписи earn/Boost/shop
  сохраняй, пока задача не требует локализации.
- Не удаляй неиспользуемые компоненты/референсы и не делай массовый рефакторинг в несвязанной задаче.

## Figma

При реализации дизайна из Figma сначала прочитай `.agents/skills/figma-design-to-code/SKILL.md`.
Он обязателен перед `get_design_context`. Для изменения только Markdown-контекста не нужен.
Локальные экспорты помогают сверке, но не подтверждают актуальность удалённого макета.

## Проверки

Для изменения кода выполни `npm run lint` и `npm run build`.
Тестового runner и команды `npm test` сейчас нет; не описывай сборку как проверку игровых сценариев.
Для документации достаточно сверки фактов, ссылок и diff; повторять сборку без причины не нужно.
Записывай фактические результаты, предупреждения и непроверенные сценарии в STATE/CURRENT_TASK.

При затрагивании поведения вручную проверь соответствующие сценарии:

- Тап даёт монеты и расходует энергию; при нулевой энергии награды нет; регенерация ограничена максимумом.
- Улучшения и здания списывают правильную цену, соблюдают ограничения, меняют характеристики/доход.
- Задания выдают награду один раз; буст имеет срок и множитель; магазин корректно меняет валюту/энергию.
- Перезагрузка восстанавливает прогресс, offline-прогресс соответствует ожидаемому, сброс работает после подтверждения.
- Все пять вкладок, модалки, закрытие, прокрутка и навигация доступны на мобильном viewport.
- Для Telegram-интеграции отдельно проверь реальный Telegram WebView; браузер не подтверждает haptic и поведение Telegram API.

В текущей Windows-песочнице сборка может завершиться `spawn EPERM` при загрузке Vite config.
Это встречалось 2026-10-31; повтор с разрешением запуска вне песочницы прошёл успешно.
Отмечай такое ограничение среды отдельно от ошибки приложения.

## Завершение и передача

- В CURRENT_TASK сохрани результат, проверки и оставшийся шаг; при новой задаче замени карточку,
  а значимую историю перенеси в CHANGELOG.
- В STATE обнови дату, базовый коммит, состояние проверок и конкретные ограничения.
- В ARCHITECTURE/PROJECT вноси только изменения устойчивых фактов; не дублируй журнал действий.
- В CHANGELOG добавляй важные изменения и причины, а не каждую правку строки.
- Предложения явно помечай как предложения: они не становятся согласованным планом.
- Не коммить и не отправляй изменения автоматически. Учитывай, что push в `main` запускает deployment.
- Не сохраняй секреты и личные данные; используй только имена переменных и placeholders.
